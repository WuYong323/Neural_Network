### 本周必须掌握的核心公式（先看懂再写代码）

```
网络结构：X(N,784) → Z1=XW1+b1(N,256) → A1=ReLU(Z1) → Z2=A1W2+b2(N,10) → A2=softmax(Z2)

前向传播：
  Z1 = X @ W1 + b1         # (N, 256)
  A1 = ReLU(Z1)            # (N, 256)
  Z2 = A1 @ W2 + b2        # (N, 10)
  A2 = softmax(Z2)         # (N, 10)  ← 预测概率
  L  = -mean(sum(Y * log(A2), axis=1))   # 交叉熵loss

反向传播（6个公式，必须手推一遍）：
  dZ2 = A2 - Y             # (N, 10)   ← softmax+交叉熵合并后最简形式
  dW2 = A1.T @ dZ2 / N    # (256, 10)
  db2 = sum(dZ2, axis=0) / N            # (10,)
  dA1 = dZ2 @ W2.T        # (N, 256)
  dZ1 = dA1 * (Z1 > 0)   # (N, 256)  ← ReLU导数：正数为1，负数为0
  dW1 = X.T @ dZ1 / N    # (784, 256)
  db1 = sum(dZ1, axis=0) / N            # (256,)

参数更新：
  W -= lr * dW
  b -= lr * db
```

### 本周必须想清楚的核心概念（看视频时带着这些问题）

```
1. 计算图（Computation Graph）：
   每个 Value 对象记录：自己的值 data、梯度 grad、产生它的运算 _op、它的"父节点" _prev。
   这样从最终的 loss 出发，能回溯所有参与计算的中间量。

2. 链式法则的本地实现：
   每个运算节点只关心"我对我的输入贡献多少梯度"——这就是 _backward 闭包做的事。
   c = a + b      →  c.grad 流向 a 和 b 时，各加 c.grad（加法的本地导数是1）
   c = a * b      →  c.grad 流向 a 时加 b * c.grad；流向 b 时加 a * c.grad
   c = a.tanh()   →  c.grad 流向 a 时加 (1 - c.data**2) * c.grad

3. 反向传播 = 拓扑排序 + 逐节点调用 _backward：
   先 topological sort（保证一个节点的梯度被使用前已经累加完毕），
   再从最后一个节点开始，按逆拓扑序依次调用 _backward。

4. 梯度累加（关键 bug 来源）：
   同一个 Value 在计算图中出现多次时，梯度必须 += 而不是 =。
   反例：x = Value(2); y = x + x; y.backward()。如果用 =，dx 会是 1；正确答案是 2。

5. bigram 语言模型本质：
   把训练集里每个 (前一个字符, 后一个字符) 计数 → 归一化成 P(下个字符 | 当前字符) 的转移矩阵。
   神经网络版本：用 27×27 的权重矩阵 W 替代计数矩阵，用交叉熵训练，最终学到的 softmax(W) 应接近计数归一化的结果。
```

### 本周必须想清楚的核心概念（看视频时带着这些问题）

```
1. Embedding 不是"花式 one-hot @ W"——它是 lookup
   - 数学上：one-hot @ W 等价于"取 W 的某一行"
   - 工程上：one-hot @ W 是 V × E 次乘加，embedding lookup 是 1 次内存访问
   - 工业影响：LLM 词表 5万 × hidden_dim 4096 = 200M 参数，embedding table 是 GB 级别
              推理时 embedding lookup 是"完全内存带宽 bound"——没有计算，只有取数
   - 这是 §Q9 你写的"one-hot @ W 等价于取 W 一行 → 稀疏更新 → 优惠券 3"的工程版本

2. 上下文窗口（block_size）= 现代 LM 序列长度的雏形
   - bigram: block_size=1（只看前 1 个字符）
   - EP3 MLP: block_size=3（看前 3 个字符）
   - GPT-2: 1024；GPT-4: 8K-128K；现代长上下文：1M
   - 复杂度增长：Attention 是 O(n²)——这就是为什么长上下文是 AI Infra 的核心战场

3. 初始化为什么是"能不能训"的问题，不是"训得快不快"的问题
   - 初始 loss 应该是 -log(1/V) ≈ log(V)，不是 20+
   - 看到初始 loss 27（V=27 类）说明 logits 分布非常不均
   - kaiming / xavier 的本质：让前向激活方差稳定 → 反向梯度方差稳定 → 不爆不消
   - 工业影响：FP16 训练时初始化稍微不对就溢出；BF16/INT8 量化对初始化更敏感

4. BatchNorm 的训练 vs 推理双行为（本周最重要的工业知识）
   - 训练：用当前 batch 的 mean/var，并维护 running_mean/running_var（EMA）
   - 推理：用 running_mean/running_var，**不依赖当前 batch**
   - 为什么必须有两套？推理时可能 batch_size=1（单请求），用单样本统计直接崩
   - 工业延伸：
     a) Fused BN-Conv：推理时 BN 是仿射变换，可以合并到前面 Conv 的 weight 里 → 推理零开销
     b) Frozen BN：fine-tune 时把 BN 设为 eval 模式（detection / segmentation 标配）
     c) 量化 BN：INT8 量化 Conv-BN-ReLU 序列前必须先 fuse
   - 这正对应你 autograd_explained.md §5.1 里"model.eval() 关掉了什么"——BN 是 .eval() 行为改变最显著的算子

5. Adam 的工业地位 + 它的代价（呼应 autograd_explained §5.2）
   - Adam 维护 m, v 两个 momentum 状态 → 每个参数额外占 2× 显存
   - 7B 模型用 FP32 训练：参数 28GB + 梯度 28GB + Adam 状态 56GB = 112GB
   - 推理时这三项全部消失，只留 28GB（甚至 INT8 量化后 7GB）
   - 这是为什么"训练 7B 要 A100 80G，推理 70B 也能跑 A100 80G"——Adam state 是显存大头之一
   - 工业延伸：ZeRO/FSDP 分片优化器、8-bit Adam、Adafactor（牺牲精度省显存）
```

#### Day 5（2026-05-22，周五）- EP4 下半：BatchNorm 训练/推理双行为（本周核心）

> **今天是整个第4周最重要的一天**。BatchNorm 的训练/推理双行为是你 AI Infra 路径上的第一个"具体的、可摸到的、工业每天都在处理的"问题。

- 算法（1.5h）：数位 DP 实战——P4124（CQOI2016 手机号码）或同难度题
- DL（3h）：
  - 看 EP4 第 1:00-end：
    - 实现 BatchNorm1d：
      ```python
      class BatchNorm1d:
          def __init__(self, dim, momentum=0.1, eps=1e-5):
              self.gamma = torch.ones(dim)
              self.beta = torch.zeros(dim)
              # 训练状态：running stats
              self.running_mean = torch.zeros(dim)
              self.running_var = torch.ones(dim)
              self.training = True
          def __call__(self, x):
              if self.training:
                  mean = x.mean(0, keepdim=True)
                  var = x.var(0, keepdim=True)
                  # 更新 running stats（EMA）
                  with torch.no_grad():
                      self.running_mean = (1-momentum)*self.running_mean + momentum*mean
                      self.running_var = (1-momentum)*self.running_var + momentum*var
              else:
                  mean = self.running_mean
                  var = self.running_var
              x_hat = (x - mean) / (var + eps).sqrt()
              return self.gamma * x_hat + self.beta
      ```
    - 把 BatchNorm 插到 MLP 的 hidden 层之后，重新训练，看 loss 收敛速度
  - **AI Infra 锚点（写到 `tech_notes/batchnorm_inference.md`）—— 本周最重要的笔记**：
    - **§1 训练 vs 推理双行为**：训练用 batch 统计 + 维护 EMA；推理用 running stats，与当前 batch 无关
    - **§2 为什么必须双行为**：推理时可能 batch_size=1（单请求服务），用单样本统计 mean=x, var=0，归一化直接除零
    - **§3 Fused BN-Conv（推理优化经典）**：
      - 推理时 BN 是仿射变换 $y = \gamma (x - \mu)/\sqrt{\sigma^2+\epsilon} + \beta$
      - 前面是 Conv $x = Wx' + b$
      - 合并：$y = W'x' + b'$，其中 $W' = \gamma W / \sqrt{\sigma^2+\epsilon}$, $b' = \gamma(b-\mu)/\sqrt{\sigma^2+\epsilon} + \beta$
      - **推理时 BN 算子完全消失**——这是 TensorRT / ONNX / TorchScript 都会做的标准优化
    - **§4 Frozen BN**：fine-tune 大模型时 BN 一律设为 eval 模式，避免小 batch 污染 running stats
    - **§5 与你 `autograd_explained.md §5.1` 的连接**：`model.eval()` 关掉的最重要的算子就是 BN（其次是 Dropout）
  - 顺便看一眼 PyTorch 源码 `torch/nn/modules/batchnorm.py` 的 `_BatchNorm.forward`，看真实工业代码怎么写 `if self.training` 分支

    - 直觉类比："im2col 就是把每个滑窗位置摊平成一行，然后做一次大矩阵乘——把卷积的 4D 嵌套循环变成 GPU 最擅长的 GEMM"
    - 手写 numpy 版（写到 `src/im2col_numpy.py`），跑出来和 PyTorch `F.conv2d` 在小输入上数值一致（误差 < 1e-5）
    - **AI Infra 锚点**：cuBLAS/cuDNN 的 `implicit GEMM` 是 im2col 的现代版本（不显式拷贝），思想完全一样——**GPU 卷积的本质是矩阵乘**
  - **FLOPs vs MAC vs latency 三角关系（1h，写到 `tech_notes/flops_vs_latency.md`）**：
    - **MAC**（Memory Access Cost）= 读输入 + 读权重 + 写输出 的字节数
    - **arithmetic intensity** = FLOPs / MAC（单位 ops/byte）
    - 1×1 Conv：intensity 低 → memory-bound（瓶颈是带宽）
    - 3×3 Conv：intensity 高 → compute-bound（瓶颈是算力）
    - **工业延伸（反直觉案例）**：MobileNet depthwise separable 把 FLOPs 降 8-9 倍，**实测延迟只降 2-3 倍**——因为 dw conv 是 memory-bound 的，省 FLOPs 没用，只能省带宽

  - **手写 BasicBlock 和 Bottleneck（1.5h，写到 `src/resnet_blocks.py`）**：
    ```
    BasicBlock（ResNet-18/34）：
    out = ReLU(BN(Conv3x3(x)))
    out = BN(Conv3x3(out))
    out += shortcut(x)   # 这一行是核心
    out = ReLU(out)
    ```
    - 关键 debug 点：`shortcut` 何时是 identity、何时是 `Conv1x1+BN`（维度变化时）
  - **梯度流分析（1h，写到 `tech_notes/residual_grad_flow.md`）**：
    - 数学：`∂L/∂x = ∂L/∂y · (∂F/∂x + 1)` —— 那个 `+1` 是关键
    - 直觉类比：高速公路的辅路（`F(x)`）+ 主路（`x`）—— 即使辅路堵车（梯度消失），主路保证你能开下去
    - 实证小实验：写一个 50 层全 Linear 网络，对比"加 skip" vs "不加 skip"在第一层的梯度幅度——后者会指数衰减
    - **工业锚点**：
      - Transformer 的 `x + Attention(LN(x))` 用同一个机制
      - 预激活 ResNet（pre-activation）：BN/ReLU 放在 Conv 前，对 200+ 层网络更稳定 —— LLaMA 用的就是 pre-norm

### 本周必须想清楚的核心概念（看视频时带着这些问题）

```
1. Self-Attention 的本质（不要被"注意力"这个词唬住）：
   - Q/K/V 三个投影：Query="我想找什么"，Key="我有什么标签"，Value="我携带什么信息"
   - 类比：每个 token 发一张"征友帖"(Q)，看所有人的"个人标签"(K)，按匹配度(QKᵀ)
     给每个人分配注意力权重(softmax)，再按权重加权汇总大家的"自我介绍"(V)
   - QKᵀ 是 (T, T) 矩阵 = 每个 token 对每个 token 的相似度 → 这就是 O(T²) 的来源

2. 为什么 Attention 是 O(n²)（AI Infra 第一性命题）：
   - 序列长 n，每个 token 要和所有 n 个 token 算相似度 → n×n 次
   - 这就是 W4 写过的"长上下文是 AI Infra 核心战场"的数学根源
   - GPT-2: 1024；GPT-4: 128K；长上下文: 1M —— n² 让显存和算力都爆炸

3. Causal mask（因果掩码）：
   - 自回归语言模型"预测下一个词"，第 t 个 token 只能看 1..t，不能偷看未来
   - 实现：把 QKᵀ 矩阵的上三角(未来位置)填成 -inf，softmax 后变 0
   - 下三角结构 → 这也是后面 KV Cache 能成立的前提（历史不变）

4. 残差流（residual stream）：
   - Block 里两条 x + sublayer 通路，和 W5 残差同源（那个 +1 让梯度直达）
   - pre-norm（x + sublayer(LN(x))，GPT/LLaMA 用）vs post-norm（原始 Transformer）

5. LayerNorm vs BatchNorm（呼应 W4 batchnorm_inference.md）：
   - BN 跨样本统计 → 推理 batch=1 时崩；LN 是 per-token 归一化，不依赖 batch
   - 这是 W4 "BN 双行为很麻烦"问题的终极解法：LM 干脆不用依赖 batch 的归一化

6. KV Cache 的根本（W8 推理优化的核心伏笔）：
   - 朴素自回归：每生成 1 个 token 把整个序列重新 forward → 重算了历史的 K/V
   - 但历史 token 的 K/V 根本没变！→ 缓存它们，每步只算新 token → O(n²) 降到 O(n)

7. prefill vs decode（LLM 推理两阶段，生产系统的分水岭）：
   - prefill：一次性处理整个 prompt（大矩阵乘，compute-bound）
   - decode：逐 token 生成（受 KV Cache 读取带宽限制，memory-bound）→ 呼应 W5 Roofline
```

    # x: (B, T, C)   head_size = head_dim
    q = self.query(x)                                  # (B, T, hs)
    k = self.key(x)                                    # (B, T, hs)
    v = self.value(x)                                  # (B, T, hs)

    ```python
    class MultiHeadAttention(nn.Module):
        def __init__(self, n_head, n_embd):
            super().__init__()
            self.heads = nn.ModuleList([Head(n_embd // n_head) for _ in range(n_head)])
            self.proj = nn.Linear(n_embd, n_embd)   # 拼接后的投影
        def forward(self, x):
            out = torch.cat([h(x) for h in self.heads], dim=-1)  # 并排拼接
            return self.proj(out)
    ```

    ```python
    # decode 阶段：x 只有 1 个新 token (B, 1, C)
    k_new, v_new = self.key(x), self.value(x)          # 只算新 token
    k = torch.cat([past_k, k_new], dim=1)              # 拼上历史缓存
    v = torch.cat([past_v, v_new], dim=1)
    wei = (self.query(x) @ k.transpose(-2,-1)) * scale # (B, 1, T_total)
    out = F.softmax(wei, -1) @ v                        # 只为新 token 算输出
    return out, (k, v)                                  # 返回更新后的缓存
    ```

### 逐日任务

- **Day 1（周一）—— Roofline：把 memory-bound 从"我以为"变成"我算过"**
  - 严格定义算术强度 = FLOPs / bytes；Roofline 屋顶（peak FLOP/s）+ 斜坡（带宽×强度）+ ridge point（屋顶÷带宽）。
  - **算 H100 ridge point**：FP16 ≈ 990 TFLOP/s ÷ HBM3 ≈ 3.35 TB/s ≈ **295 FLOP/byte**——即每搬 1 byte 要做够 ~295 次浮点运算才不被带宽拖累；decode 远低于它 → 必然 memory-bound（W6 §5.3 的定量证据）。⚠️ 用 `nvidia-smi -q` 确认你这张卡 SXM/PCIe、80/94G，数字要对应真实硬件。
  - 动手：对 nanoGPT decode 逐类算子估 FLOPs/bytes，画 Roofline 散点图。

#### Day 1（周一）—— Triton 编程模型:vector-add,把"一个 program 处理一块数据"刻进脑子

> **今天不追性能,只把 Triton 的心智模型建对**。Triton 和 CUDA 最大的思维差异:CUDA 你管每个 **thread(线程)**,Triton 你管每个 **program(程序实例,处理一整块数据)**。搞混这一点,后面全乱。

- **学习目标问题（能脱口而出再往下）**：
	1. Triton 的 `pid = tl.program_id(0)` 和 CUDA 的 `threadIdx` 有什么本质区别?为什么说 Triton 是"**分块(block-level)**编程"而不是"分线程"?
	2. `tl.load(ptr + offs, mask=mask)` 里的 `mask` 是干嘛的?为什么最后一个 block 处理不满 BLOCK 个元素时会越界、必须靠 mask?
	3. `BLOCK: tl.constexpr` 为什么必须是编译期常量?它和 GPU 的 occupancy(占用率,W7 Day2 ncu 那个)有什么关系?
- **动手（Track A,~4h）**：
	- 跟 Triton 教程 01,手写 `vector_add`:`c = a + b`,百万级元素。**先跑通,再逐行讲清"这个 program 负责哪一段 offs、mask 挡住了谁"**。
	- 对标 baseline:同一份数据,量 `torch 原生 a+b` vs `torch.compile` vs 你的 Triton kernel,用 W7 Day2 的 `torch.cuda.Event` 计时法(warmup=30/iters=100)。**预期:elementwise 这种 memory-bound 小算子,你的 Triton 大概率和 torch 原生持平**——这正常,教学意义在"我能写对",不在"我更快"。
	- 误差验证:`torch.allclose(out_triton, out_ref)`——elementwise 应逐元素几乎相等(尺子①,W7 Day6 §6.2)。
- **底层理解锚点（写进笔记）**：画一张图——1M 个元素怎么被切成 `ceil(1M/BLOCK)` 个 program,每个 program 内部 `tl.arange(0,BLOCK)` 生成的向量下标,GPU 怎么把这些 program 铺到 SM 上并行。**这就是 W7 Day4 §2 "launch 一个 kernel"里被启动的那个 grid,今天你第一次亲手定义它的形状。**
- **Track B（~1h,起步）**：H100 上 `module load CUDA/12.4` → `amk compile small --gpu h100` 跑通,确认环境没坏(接 W7 AMK 进度锚点)。

#### Day 2（周二）—— fused pointwise:亲手把 W7 Day4 的"第二笔账"省出来

> 今天开始碰**真正的价值**。W7 Day4 你量出"中间张量落 HBM"是笔浪费、W7 Day5 你读了 Inductor 自动融合的代码——**今天你自己写这个融合 kernel**,并实测它比"不融合"省了多少。

- **学习目标问题**：
	1. `relu(x*a+b)` 不融合是 3 个 kernel、融合是 1 个。省的两笔账(启动 + 访存)在你的 Triton 代码里**分别对应哪几行**?（提示:launch 次数看你调几次 kernel;访存看 `tl.load`/`tl.store` 几次 vs 中间量留寄存器）
	2. 为什么 pointwise(逐元素)算子最好融?什么样的算子**不能**简单融进来?(接 W7 Day5 §4.3 融合边界)
	3. 张量多大时,融合的加速才明显?为什么小张量融了也白融?(接 W7 Day4:小张量是 launch-bound,省访存无感)
- **动手（Track A,~4h）**：
	- 写 `fused_mul_add_relu` 的 Triton kernel（就是 W7 Day5 §4.2 你读过的那段的**手写版**):一次 `tl.load` 读 x/a/b → 寄存器里连算 `x*a+b` 再 `tl.maximum(·,0)` → 一次 `tl.store`。
	- **三方对标**:①朴素 3 次 torch 算子 ②`torch.compile(mode="max-autotune")` ③你的手写 kernel。张量开到足够大(如 8M~64M 元素,确保 memory-bound)。记录加速比。

- **底层理解锚点**：对照你 Day2 的 kernel 和 W7 Day5 §4.2 Inductor 自动生成的版本——**结构几乎一样**。写进笔记:"我手写的和 Inductor 自动生成的差在哪?"（多半差在 autotune 的 BLOCK 选择、循环展开——这就引出 Day3 的调优）。

#### Day 3（周三）—— reduction + 调优:RMSNorm/softmax,从"逐元素"跨到"跨元素"

> 今天是**质的跳跃**。前两天的 pointwise 每个元素独立;今天的 **reduction(归约)** 要"把一行/一列的很多元素汇总成一个数"(求和、求 max),这需要 program 内部协作——是 LayerNorm、softmax、attention 的核心操作,也是真实 LLM kernel 的第一道坎。

- **学习目标问题**：
	1. 什么是 **reduction(归约)**?为什么 `x.sum(dim=-1)` 比 `x+y` 难写成 kernel?（提示:逐元素输出形状不变,归约要"塌缩"一个维度,program 内的多个数据要互相通信）
	2. softmax 为什么必须"**减去最大值再 exp**"?（数值稳定,接 W7 Day6 §4 FP16 溢出:不减 max,`exp(大数)` 直接 inf）
	3. **RMSNorm** 比 LayerNorm 少算了什么?为什么现代 LLM(LLaMA)用 RMSNorm?（少算均值,只用均方根;更少的 reduction = 更快,且效果不降）
	4. Triton 的 `tl.autotune` 在调什么?BLOCK 太小/太大分别会怎样?（太小 occupancy 高但每 program 干活少、launch 多;太大寄存器/shared memory 不够、occupancy 崩——W7 Day2 ncu 的占用率概念）
- **动手（Track A,~4h）**：
	- 写 `rmsnorm` 的 Triton kernel:一个 program 处理一行,`tl.load` 整行 → 算 `x / sqrt(mean(x²)+eps) * weight` → `tl.store`。**这里 `mean(x²)` 就是你第一个 reduction**（`tl.sum(x*x)/N`）。
	- 加 `@triton.autotune`,给几组 `BLOCK_SIZE` / `num_warps` 候选,让它自动选最快——**体会 W7 Day5 `max-autotune` 到底在替你做什么**。
	- **三方对标**:`torch.nn.functional`(或手写 eager)vs `torch.compile` vs 你的 kernel。RMSNorm 是 memory-bound,融合 + 单 kernel 应该能打平甚至略胜 torch。
	- 误差:reduction 会改变浮点累加顺序,**这里 allclose 可能需要放宽 rtol,正好用上 W7 Day6 §6.2 的 cosine 尺子**——写进笔记"为什么 reduction 后要从 allclose 退到 cosine"。
- **底层理解锚点**：写清"一个 program 内部怎么把 BLOCK 个数求和"——Triton 帮你隐藏了 CUDA 的 shared memory + `__syncthreads()`,但你要知道它底下就是"每个线程算部分和 → 树形归约 → 得到全行和"。**这是 CUDA 的 reduction 经典模式,Triton 用 `tl.sum` 一行封装了。**（暑假后段下沉 CUDA 时会亲手写这个树形归约）
- **Track B（~1.5h）**：读 Day2 抓的 AMK trace,用 `nsys stats` 数 decode 一步的 kernel 数、gap 占比(接 W7 Day2 方法论),记进 report 草稿。
- **产出**：`week8_triton/03_rmsnorm.py`（含 autotune）+ `tech_notes/reduction_and_autotune.md` + 三方数据 + "allclose→cosine 为何退一步"分析。
- **完成标准**：RMSNorm kernel 正确且不慢于 torch;能口述"reduction 为什么比 pointwise 难、autotune 在调什么"。

#### Day 4（周四）—— FlashAttention 的思想:为什么"不落地 T×T 矩阵"是关键（**本周理解高峰**）

> **如果本周只彻底想通一件事,就是今天**。W6 你手写的 attention 会显式生成 T×T 的注意力矩阵(`wei = q@k.T`);W7 你知道 decode 是 memory-bound。今天把这两件事撞在一起:**FlashAttention 的核心不是新数学,是"把 softmax 融进 attention,让那个 T×T 矩阵永远不落 HBM"**——这正是你 Day2 的"第二笔账"在 attention 上的终极形态,也是你未来巨核要复现的核心技巧。

- **学习目标问题**：
	1. 标准 attention 为什么是 memory-bound?（手算:`q@k.T` 生成 T×T 矩阵写回 HBM,softmax 再读回来,再 `@v`——一个 T×T 矩阵在 HBM 往返好几趟,W6 §attention_complexity 你算过 T=1024 单头就 4MB）
	2. **online softmax(在线 softmax)** 是什么?为什么它能让 softmax "边算边更新、不需要先看到整行"?（这是 FlashAttention 不落地 T×T 的数学关键:分块算,维护 running max 和 running sum 增量修正）
	3. FlashAttention 省的是**哪笔账**?（主要是访存——T×T 中间矩阵不落 HBM,留在 SRAM/寄存器;呼应 W7 Day4 第二笔账,是它在 attention 上的极致применение）
- **动手（Track A,~4h,今天以理解 + 读为主,写为辅）**：
	- 读 FlashAttention 论文摘要 + §3.1,**对照 W6 你手写的 attention**,标出"我那版哪一步把 T×T 落回了 HBM、Flash 怎么避开"。
	- **不要求从零写完整 FlashAttention**（那是暑假后段的活）——今天写一个**简化版 fused attention**:小 T、单头,把 `q@k.T → mask → softmax → @v` 尽量融进一个 Triton kernel(可以先不做分块的 online softmax,先做"整块读进 SRAM 算完"的简化版)。目标是**亲手体会"softmax 和两个 matmul 融在一起"**。
	- 对标:`F.scaled_dot_product_attention`(PyTorch 内置的 FlashAttention)vs 你的简化版。**你大概率打不过官方——这正常且重要**:写进笔记"官方 FlashAttention 比我快在哪"(分块 online softmax、warp 级优化、tensor core),这就是你和工业级 kernel 的差距地图。
	- 误差:cosine + top-1(接 W7 Day6 §6.3,attention 输出用 cosine 最合适)。
- **底层理解锚点**：画 online softmax 的增量更新图——分块处理时,新块来了怎么用 `new_max` 修正之前累积的 `sum` 和输出。**这是 FlashAttention 唯一的"魔法",想通它你就懂了这个统治性算子。**
- **Track B（~1h）**：把 AMK 的 attention region(W7 AMK report:attention 364µs 是大头)和你今天理解的 FlashAttention 对照——AMK 巨核里 attention 是怎么处理的?为什么论文说 H100 上它打不过?（跨 SM 同步)
- **产出**：`week8_triton/04_fused_attention_simplified.py` + `tech_notes/flashattention_idea.md`（含 online softmax 增量图 + "官方比我快在哪"差距地图）。

#### Day 5（周五）—— AMK 真实 profiling 收口:把预测延迟换成实测（**Track B 高潮,科研产出**）

> 今天主线切到 **Track B**,是你科研的实打实产出日。W7 你出了 AMK report v0(延迟是 **cost-model 预测**、GPU 路径未接通)。今天用你 Day1-4 练出的 kernel/profile 直觉 + W7 Day2 的 nsys 方法论,**把预测数换成 H100 实测数**——这是论文因 Modal 上 ncu 不可用而做不到、且点名为 future work 的事,是你相较师姐 Gemma+vLLM 工作的**独特价值**。

- **学习目标问题**：

#### Day 6（周六）—— 端到端集成:把手写 kernel 装进 nanoGPT,和 baseline 正面决战

> 前几天的 kernel 都是"零件"。今天做**系统集成**——把你写的 RMSNorm/fused kernel 真正替换进 W6 的 nanoGPT,跑端到端生成,和 `torch.compile` baseline 做**全套对标**。这是"会改"的完整闭环:不只 kernel 快,整个模型要快、且生成结果对。

- **学习目标问题**：
	1. 单个 kernel 快 ≠ 端到端快——为什么?（Amdahl 定律:你优化的算子占端到端多少比例决定上限;若 RMSNorm 只占 5%,它快 2× 端到端也就快 2.5%）
	2. 集成一个自定义 kernel 要处理哪些工程问题?（形状/dtype 兼容、autograd 是否需要、和 KV Cache 的交互、回退路径）
	3. 你的手写 kernel vs `torch.compile` 整模型,谁快?差在哪?（大概率 torch.compile 整体更强——它全图融合;你单点优化只在被替换的算子上有优势。**这个诚实结论恰恰是你课题 ≥20% 的分母认知**）
- **动手（Track A,~5h）**：
	- 把 Day3 的 RMSNorm(或 Day2 fused kernel)接进 nanoGPT 的对应位置,`torch.no_grad()` 推理下跑通生成。
	- **全套对标(用 W7 全部方法论)**:①eager ②`torch.compile(max-autotune)` ③eager+你的手写 kernel ④compile+你的手写 kernel,四组端到端 tok/s + 首 token 延迟。
	- **误差三尺子全上**(W7 Day6 §6.3):逐元素 max err、logits cosine、top-1 一致率——证明换了 kernel 后生成"误差可控可解释"。
	- **写清诚实结论**:你的手写 kernel 在哪个对标里赢了、哪个输了、为什么。**这比"我快了 N×"重要一百倍**——它是你判断"手写巨核值不值得做、该攻哪个算子"的依据(直接服务小米课题决策)。
- **产出**：`week8_triton/06_nanogpt_integrated.py` + `tech_notes/end_to_end_showdown.md`（四组对标 + 三尺子误差 + 诚实结论）。
